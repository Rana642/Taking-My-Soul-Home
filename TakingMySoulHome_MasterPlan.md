## 2. Tech Stack & Architecture

- **Frontend:** React 19 + TypeScript, Vite 6, Tailwind CSS v4
- **Target architecture: Headless** — WordPress as backend/CMS only (via WPGraphQL + ACF for custom content types), this React app as the fully custom frontend, connected via GraphQL queries
- **Hosting plan:** Frontend on Vercel/Netlify, WordPress backend on standard managed WP hosting (admin-only, not public-facing)
- Currently: no routing yet (single-page `activeTab` state switch) — needs `react-router-dom`
- Currently: all content is hardcoded in `src/data/mockData.ts` — will eventually be replaced by live WordPress/GraphQL data

### ✅ Step 5 — Migrate Vite → Next.js (App Router)  — DONE
**Decision locked:** move off the Vite SPA to Next.js App Router. Reason: the current setup is client-side-only rendered — bad for SEO (Bing/DuckDuckGo don't run JS, social-link previews break, initial HTML has no content). Next.js gives SSR/SSG + a native metadata & schema API, and pairs cleanly with the planned headless WordPress backend. Doing it NOW (before more pages are built) avoids re-doing Step 7's episode page and the WordPress data layer twice.
- Safety: initialise git + commit the working Vite app first (no VCS existed before this) so the migration is reversible
- Install Next.js; App Router (`app/` directory), not Pages Router
- Tailwind v4 via `@tailwindcss/postcss` (currently the `@tailwindcss/vite` plugin); keep `index.css` `@theme` block as-is
- Root `app/layout.tsx`: fonts (Higuen `@font-face` + Open Sans via `next/font` or link), global styles, and a client "AppShell" holding the modal/audio/search state that `App.tsx` currently owns
- File-based routes mirroring the current URL map: `/`, `/about`, `/series`, `/episodes`, `/blog`, `/blog/[slug]`, `/resources`, `/community`, `/contact`, `/legal/[type]`, `not-found`
- Convert routing primitives: `react-router-dom` `Link` → `next/link`, `useParams` → route segment props, `useNavigate` → `useRouter`, `<Navigate>` → `redirect()`; add `"use client"` to the interactive components (modals, audio player, search, hero, prayer widget)
- Move the `.htaccess` SPA-fallback concern away — Next handles routing; hosting shifts to Vercel (see Step 13)
- Remove Vite (`vite.config.ts`, `@vitejs/plugin-react`, `index.html`, `main.tsx`) once Next builds clean
- Done when `next build` passes and every route renders server-side (view-source shows real content)

## 6. Key Decisions Already Made (don't re-litigate these)

- **Architecture:** True headless (WordPress backend + custom React frontend), not a simple WordPress theme, not a fully independent app with a custom blog editor
- **Community page:** Kept, not removed, despite being outside the original target list
- **Logo:** Real uploaded brand asset takes full priority over any AI-generated placeholder
- **Colors/fonts:** Fully locked per the official Crea8ovia brand guide — no deviation without explicit user approval
- **SEO priority:** Real routing + proper meta/schema setup is treated as a hard requirement, not a nice-to-have, because SEO/organic growth is the core business goal behind this whole rebuild
- **Rendering framework:** Migrating Vite → **Next.js (App Router)** for SSR/SSG — required for real SEO. Locked (was open question in §7).
- **Language:** **English only.** No Urdu/bilingual. No `hreflang`, no `/en` `/ur` URL split — keep URLs flat.
- **Hosting (locked):** frontend (Next.js) → **Vercel** (Hobby/free, auto-deploy from GitHub, full SSR/ISR — no static export). WordPress backend → **Hostinger** (Shared/Premium plan) on a subdomain e.g. `cms.takingmysoulhome.com`, admin-only/headless. User considered all-Hostinger but chose Vercel to keep ISR (live content updates) without a rebuild-and-reupload workflow.
